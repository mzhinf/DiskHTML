# 代码库现代化重构计划

## 目标与原则

本计划在不改变现有行为、数据格式和公共 API 的前提下，逐步降低 DiskHTML 的维护成本。每个重构批次只处理一个关注点，必须可以独立审查、独立回退，并用目标测试和完整回归共同证明行为稳定。

本轮基线为：

- Python 3.12，运行时无第三方依赖；
- Ruff 检查通过；
- 128 项 `unittest` 全部通过；
- 当前 HTML 格式版本、SQLite 模式版本和比较语义保持不变；
- `diskhtml`、`diskhtml-gui`、`python -m diskhtml`、发布 EXE 参数入口和已有 Python 兼容名称保持可用。

## 现状结论

### 死代码与未采用抽象

- `scripts/verify_release.py` 的 `_validate_embedded_project_version` 没有调用方，相关版本读取导入也只服务于该函数，属于可直接删除的内部死代码。
- `models.py` 中的 `ScanJob`、`VolumeInfo`、`FileRecord`、`CompareResult`、`ErrorRecord` 仅在定义处出现；`util.format_size` 也没有调用方。
- 上述名称没有前导下划线，删除前必须先确认公共 Python API 边界。普通清理批次不得仅凭仓库内无引用就删除它们。
- 运行链仍主要传递 `sqlite3.Row`、`dict[str, Any]` 和 `Any`，说明强类型领域数据类没有真正成为持久化边界。这一取舍应通过独立 API/领域模型决策解决。

### 重复路径与边界泄漏

- `cli.py` 与 `exe_cli.py` 分别维护扫描参数声明和 `argparse.Namespace` 到 `ScanConfig` 的合并规则，公共字段重复且 Hash 策略能力已经发生漂移。
- `html_archive.py` 导入 `compare._iter_entries`，`compare_exporter.py` 导入 `exporter` 的四个私有函数；跨模块共享与私有命名约定冲突。
- `Database` 的逐条事务入口与 `DatabaseBatch` 的批量入口同名并存。它们当前承担不同事务语义，不能直接合并或删除，但底层 SQL 和参数归一化可以共用。
- Python、桌面 UI 和离线浏览器分别存在大小、状态和 Hash 策略显示逻辑。不同运行环境不能强行共用代码，但应共用契约数据和等价测试。

### 体量与变化热点

- `ui.py` 是最大且变更最频繁的业务模块，包含布局、表单状态、校验、任务编排、线程事件和语言切换。
- `scanner._hash_file` 约 97 行；`scanner._iter_paths` 约 76 行且分支密集，混合了路径枚举、链接处理、排除规则和错误持久化。
- `database.py` 同时包含 schema、初始化、事务、仓储、批量写入和项目自检。
- `archive_ui.py` 内嵌约 26,000 字符 JavaScript 和约 8,000 字符页面头，现有 Python 质量工具无法直接分析浏览器代码。
- `scripts/release_licenses.py` 总体积大，但主要由多个相对独立的组件识别规则组成；它不是首批拆分对象。

### 陈旧与兼容表面

- `ScanOptions = ScanConfig`、`ui_text.__getattr__`、`compare-html`、高级 SQLite CLI 和数据库逐条写入口都有现有测试或文档承诺，属于兼容表面，不是普通死代码。
- `Database.migrate()` 和 `init-db` 的“迁移”命名与当前“只接受版本 0 或当前版本、拒绝旧版本”的实际行为不完全一致。
- `docs/rework-analysis.md` 声称 CI 会构建和验证发布包，但当前 CI 只执行格式、Ruff 和单元测试；该描述已经过期。

## 实施前应建立的规格与等价检查

在修改高耦合模块前，先增加以下维护资产：

1. `docs/public-api.md`：列出稳定入口、命令、退出码、可导入名称、兼容别名、HTML/SQLite 格式版本和弃用规则。
2. `docs/refactor-baseline.md`：记录 128 项测试基线、支持平台、质量命令、已知非确定字段和人工验收范围。
3. 确定性 parity 夹具：覆盖空目录、中文与特殊字符、大小文件、采样与完整 Hash、权限错误、软链接/重解析点、暂停/取消/恢复和六种比较状态。
4. CLI 契约快照：比较两套 CLI 的命令、参数顺序、默认值、帮助文本、标准输出/错误和退出码。
5. 数据等价检查：比较 SQLite schema、索引、状态迁移、行语义与 HTML 载荷；UUID、时间和临时绝对路径先规范化，不做脆弱的原始字节比较。
6. 离线 HTML 真实浏览器测试：从 `file://` 打开，执行目录树、面包屑、搜索、排序、详情、语言切换、盘符切换和 CSV 导出，并保存关键截图。
7. Tk UI 基线：保存三任务页的中文/英文、最坏错误状态和运行区展开截图。任何 UI 源码重构前先由维护者确认该原型就是应保持的视觉基线。

## 可审查重构批次

### 批次 0：冻结行为与公共边界

当前行为：128 项测试通过，但没有公共 API 清单、CLI 帮助快照、真实浏览器回归或 UI 截图基线；部分文档与 CI 事实不一致。

结构改进：先添加上述 API、行为基线、确定性夹具和等价检查；修正 CI 与迁移能力的文档描述，不改变程序输出。

稳定性验证：文档索引、链接和编码测试通过；基线夹具在未修改业务代码的提交上通过；现有 128 项测试结果不变。

### 批次 1：删除已证实的内部死代码

当前行为：发布验证从不调用 `_validate_embedded_project_version`，最终校验仍通过 EXE `--version`、包结构、许可证和真实快照冒烟完成。

结构改进：删除该私有函数及仅由它使用的导入；对公开命名但未使用的领域类和 `format_size` 只登记，不在本批删除。

稳定性验证：全仓搜索确认没有剩余引用；`test_verify_release_script`、版本测试、构建脚本测试和完整测试通过；真实发布包验证命令保持成功。

### 批次 2：统一两套 CLI 的扫描配置合并

当前行为：高级 CLI 与 EXE CLI 分别声明相同扫描参数并各自合并配置默认值；相同字段的结果应一致，但功能集合不同。

结构改进：提取不包含命令分派的共享参数声明与 `ScanConfig` 合并函数；各入口仍决定是否暴露 Hash 策略，命令名、参数顺序、帮助文本和退出码保持不变。

稳定性验证：新增表格驱动测试，对两套入口的公共参数生成相同 `ScanConfig`；锁定帮助文本和错误输出；运行配置、CLI、EXE CLI、GUI 入口和完整测试。

### 批次 3：整理报告层共享私有函数

当前行为：比较报告导出器从普通报告导出器导入四个私有函数，发布目录、CSV、JSON 和行转换语义由名称上不公开的实现维持。

结构改进：把真正共享的发布和序列化函数移动到 `report` 包内明确的内部模块；两个导出器只保留各自的清单、分片和页面逻辑。

稳定性验证：对同一确定性数据库比较规范化后的 CSV、JSON、清单和 HTML；运行导出、比较、路径锁重试及完整测试。

### 批次 4：收紧比较与 HTML 应用服务边界

当前行为：`html_archive.py` 直接使用 `compare._iter_entries` 生成内存比较载荷，数据库比较路径也依赖同一算法。

结构改进：把“两个已排序行流生成比较条目”提升为明确的领域内部接口，调用方不再依赖下划线私有实现；状态判定顺序和消息完全不变。

稳定性验证：对 `MATCH`、`PRECHECK_MATCH`、`CHANGED`、`ADDED`、`MISSING`、`ERROR` 做顺序和字段级等价断言；运行比较、HTML、导出和完整测试。

### 批次 5：拆分数据库 schema 与项目自检

当前行为：`database.py` 同时保存建表 SQL、版本校验、事务、仓储和项目自检；旧数据库被明确拒绝，不执行升级。

结构改进：先把 schema 常量与校验移动到内部 schema 模块，再把 `project_check` 的各项规则提为命名查询/判定函数。`Database` 类、方法签名、事务边界和错误文本保持不变。

稳定性验证：比较 `sqlite_master`、`PRAGMA table_info`、索引、迁移记录与项目自检问题顺序；运行数据库、扫描恢复、比较、HTML 重渲染和完整测试。

### 批次 6：统一数据库写入的底层实现

当前行为：逐条写入口每次开启独立事务，扫描主循环使用批量事务；两者都是现有兼容 API。

结构改进：让两类入口共用私有 SQL 执行函数和参数归一化，保留逐条与批量两种提交时机。待内部调用全部迁移后再评估弃用，当前不删除公开方法。

稳定性验证：失败批次仍全部回滚，逐条写仍立即可见，扫描仍保持单写入者和有界内存；运行数据库、1 万条批量测试、扫描恢复和完整测试。

### 批次 7：简化扫描路径枚举控制流

当前行为：`_iter_paths` 同时处理单文件、目录遍历、排除规则、重解析点、路径错误和审计写入，产出顺序影响恢复与测试。

结构改进：提取纯路径分类、排除判断和错误分类函数；编排函数仍保持相同遍历顺序、跟随链接规则和错误持久化时机。

稳定性验证：用确定性夹具逐项比较产出路径及顺序、目录记录、错误码、Windows junction 和长路径结果；运行扫描器、恢复、磁盘信息和完整测试。

### 批次 8：拆分单文件 Hash 尝试与结果组装

当前行为：`_hash_file` 同时进行 stat、完整/采样 Hash、可选 SHA-512、变化检测、有限重试和结果字典组装。

结构改进：分为“单次读取尝试”“稳定性判定”“领域结果组装”三个私有步骤；不改变读取块、重试次数、摘要大小写、算法标识或错误码。

稳定性验证：参数化覆盖空文件、预算边界、大文件、完整/采样、SHA-512、读取失败、文件消失和计算期间变化；比较摘要、读取量、尝试次数与持久化记录；运行扫描、采样、恢复和完整测试。

### 批次 9：提取桌面 UI 的纯状态与校验

当前行为：`MainWindow` 同时维护 Tk 控件、表单状态、路径建议、输入校验、任务参数和语言切换，是最高频变更点。

结构改进：在已确认 UI 基线后，先提取不依赖 Tk 的表单状态、输出路径建议和任务请求构造；窗口布局、控件层级、文案、快捷行为和线程模型不变。

稳定性验证：纯逻辑单元测试、现有 Tk 测试、三任务真实流程、中文/英文截图和最坏布局截图均与基线一致；完整测试通过。

### 批次 10：提取桌面后台任务协调

当前行为：后台任务类、事件队列、暂停/继续/取消、状态面板和完成处理均与窗口类位于同一模块。

结构改进：把任务对象与事件协议移动到内部任务模块，`MainWindow` 只负责绑定和显示；保留 `diskhtml.ui:main`、线程边界和事件名称。

稳定性验证：真实后台扫描、事件顺序、暂停/继续/取消、关闭窗口、输出打开按钮和错误显示测试通过；截图、完整测试及 Windows EXE 冒烟通过。

### 批次 11：整理许可证识别规则

当前行为：许可证脚本在单文件中包含来源登记、运行库定义、各组件发现、声明生成与校验；单个函数规模尚可，但新增组件需要跨多处修改。

结构改进：先把可数据驱动的原生运行库规则整理为声明式注册表，再提取共用发现流程；所有版本和许可证来源继续从 provenance 与最终包推导，不新增硬编码副本。

稳定性验证：已知组件顺序、未知组件阻断、Qt 残留阻断、许可证哈希和声明文本保持一致；运行许可证、构建、发布验证和完整测试。

## 必须单独立项的迁移

以下工作不应混入上述行为保持型重构：

- 离线页面资源化：把 `archive_ui.py` 的 CSS、JavaScript、HTML 拆成资源并在生成时内联。这会改变构建输入和 PyInstaller 资源清单，必须在真实浏览器 parity 套件完成后单独迁移。
- 领域数据强类型化：决定采用现有数据类、`TypedDict` 或新的 DTO，并逐层替换 `sqlite3.Row`/字典。这是跨数据库、比较、HTML 和报告的架构移动。
- 公共 API 清理：移除 `ScanOptions`、动态翻译常量、未使用公开数据类、`compare-html`、高级 SQLite CLI 或逐条数据库方法。必须先发布弃用说明并设定主版本窗口。
- 数据格式变化：任何 HTML/SQLite schema、版本、状态或算法标识变化都必须独立设计迁移与兼容策略。
- 框架或平台迁移：替换 Tkinter、降低/提高 Python 最低版本、用 Win32 `DeviceIoControl` 替代 PowerShell 查询都属于独立任务。
- 依赖与交付升级：升级 PyInstaller/Ruff、正式采用锁文件、增加浏览器测试依赖、改 CI 构建/发布策略或建立自动发布流程，分别处理并验证供应链与可复现性。

## 每个批次的完成门禁

每个批次采用一个主题、一个提交，并依次满足：

1. 先运行对应模块的目标测试；
2. 运行 Ruff 格式检查与静态检查；
3. 运行全部 128 项现有测试及新增 parity 测试；
4. 运行 `git diff --check`；
5. 数据、HTML 或 CLI 相关批次比较规范化前后产物；
6. UI 或浏览器相关批次附已确认原型、前后截图和真实交互结果；
7. 构建或资源相关批次运行 Windows 构建与解压后发布包验证；
8. 同步架构、数据格式、用户指南、变更记录和文档索引中受影响的事实。

建议先完成批次 0 至 4，再依次处理数据库、扫描器和桌面 UI。离线页面资源化、领域数据强类型化及所有 API/依赖/框架变化保持为独立迁移任务。
